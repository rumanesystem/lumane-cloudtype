# 세션 복구·불일치 확인 절차

## 복구 기준

- 일반 상담은 마지막 DB 저장(`saved_at`) 후 1시간 이내에 동일 세션이 다시 요청될 때만 복구한다.
- 상담원 개입 상태는 서버 시작 시 최근 30분 이내의 `mode = 'admin'` 세션만 복구한다.
- 대화 내용과 상담원 메시지 읽음 상태는 `conversations.messages`를 정본으로 삼는다.
- 토큰 누계는 `token_stats`에서 복구한다.
- 견적 알림 완료 여부는 동일 견적번호가 `quotes`에 존재하는지 확인해 복구한다.
- fallback 전송 여부는 저장된 assistant 메시지 ID의 `fallback_` 접두사로 복구한다.
- 상담원 메시지는 읽음 처리 전까지 재전달하고 브라우저가 `mid`로 중복 제거한다. 읽음 상태는 대화 정본에 다시 저장한다.

30분이 지난 메모리 세션은 마지막 저장 후 제거한다. 저장이 실패하면 메모리에서 제거하지 않고 다음 정리 주기에 다시 시도한다.

## 운영 확인

배포나 재시작 직후 애플리케이션 로그에서 다음 항목을 확인한다.

```text
[SESSION_RECOVERY] admin_restored=<복구 수> scanned=<조회 수> window_min=30
```

선택 저장소를 조회할 수 없으면 다음과 같은 지연 로그가 남을 수 있다. 주 상담 복구는 계속 진행되며, 동일 견적의 운영 알림은 중복 발송하지 않는 쪽으로 처리한다.

```text
[TOKEN_HYDRATE_SKIP]
[QUOTE_RECONCILE_DEFER]
```

DB와 화면 상태가 다를 때는 아래 순서로 확인한다.

1. `conversations`에서 `session_id`, `mode`, `saved_at`, `messages`를 확인한다.
2. 동일 `session_id`의 `token_stats` 누계를 확인한다.
3. 신규 AI 견적은 `KB-AI-` + 전체 `session_id`의 SHA-256 앞 32자리(대문자 hex)를 견적번호로 사용한다. `quotes.quote_number`와 `customer.install.source_ref`가 동일한지 확인한다. 세션 ID 자체를 견적번호로 노출하지 않는다.
4. `saved_at`이 복구 창보다 오래됐으면 stale 세션으로 판단하고 복구하지 않는다.
5. 복구 창 안인데 화면과 다르면 애플리케이션의 `SESSION_RECOVERY`, `TOKEN_HYDRATE`, `QUOTE_RECONCILE` 로그를 확인한다.

운영 데이터는 이 절차에서 직접 수정하지 않는다. 데이터 보정이 필요하면 원인과 대상 행을 확인한 뒤 별도 마이그레이션 또는 승인된 관리 작업으로 수행한다.

PR91의 기존 번호 호환 경계: `KB-AI-<세션 끝 8자리>` 행만 존재하면 세션 소유 관계를 확정할 수 없다. `[AI_QUOTE_IDENTITY_REVIEW]` 로그를 남기고 자동 견적 등록·금액 갱신을 중단한다(채팅 견적 저장 응답은 503). 기존 행을 덮어쓰거나 새 번호로 중복 등록하지 않는다. 이 PR을 운영에 적용하기 전 기존 번호의 연결·전환 절차와 `quote_number`의 38자 수용 여부를 별도로 확인해야 한다. 이번 로컬 검수는 운영 데이터 보정을 수행하지 않았다.

## 배포 구성 경계

현재 세션 직렬화는 애플리케이션 프로세스 내부에서 동작하므로 단일 인스턴스를 전제로 한다. 여러 인스턴스로 확장하기 전에는 DB revision 또는 분산 잠금을 도입해야 한다. 그 전까지 replica 수를 늘리지 않는다.
